## Required before public release

1. **Separate local and hosted databases.** `backend/.env` points at Supabase, while the root Compose configuration targets its local PostgreSQL service. Do not run `npm run db:deploy`, `npm run test:db`, or backend server commands against the Supabase configuration during local work. Use a dedicated disposable test database for integration tests.
2. **Create a production recovery plan.** The current preview database is the existing Supabase Dev project and its schema migrations are complete. Its verified DPAPI backup is local and Windows-account-bound, not an independent recovery copy. Before real multi-user use, establish provider backups or encrypted off-site exports and rehearse a restore into an isolated database.
3. **Finish live end-to-end verification.** GitHub App authorization and installation are already verified against the deployed service, and the installation is restricted to `leetcode-solutions`. The dashboard currently has no submission in its hosted history. After the owner submits a real solution and LeetCode marks it Accepted, verify exactly one corresponding commit and a `SYNCED` record, then retry/disconnect behaviors using non-destructive checks.
4. **Complete an independent security review.** Recheck the production threat model, OAuth/App permissions, extension permissions, rate limits, logging and data deletion paths before opening signups. Automated tests and a clean dependency audit do not establish that the service is unbreachable.
5. **Choose dependable production hosting.** The current Render free preview is deployed. For public launch, select an always-on plan, reliable worker arrangement, database backups/restore, alerting, and a custom domain; keep one API instance until rate limiting uses a shared store.
6. **Finish launch materials and extension distribution.** The current provider and data-retention facts are filled into the legal draft. Obtain qualified legal review, establish and document a recoverable backup/restore policy, configure the production domain, test the packaged extension in a clean profile and the full flow on that domain, then submit it to the browser extension store.

## Remaining known limits

- A stolen extension token can still submit a fake, valid-shaped Accepted payload for an already-active link because LeetCode provides no server-verifiable receipt. Disconnecting the browser or LeetCode link revokes the token. A repository-limited GitHub App reduces the potential write scope.
- Automated tests cannot prove the service is unbreachable. The database-backed pairing regression passed against an isolated disposable PostgreSQL database; it still needs end-to-end validation through the deployed service and real extension.
- Historical backfill, Chrome Web Store publishing, and broader browser automation can follow after the release gates above.
