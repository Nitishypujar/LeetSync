# Investigation: missing dashboard submissions

**Date:** 2026-10-20  
**Scope:** Read-only source and release-record inspection on branch `codex/investigate-missing-submissions-2026-10-20`, based on `b0407ed`. No live database query, data change, deployment, or real submission was performed.

## Conclusion

The source code does not contain a dashboard filter that would hide earlier submissions by date or sync status. For the authenticated account, `/api/dashboard` selects submissions by the session's `userId`, orders them newest first, and returns up to 30; the accepted count uses the same `userId` predicate. The sync worker writes `SYNCED` only after GitHub's commit call returns a SHA, then persists the status and SHA together in a database transaction.

The strongest available clue is the prior read-only Supabase preflight recorded in `docs/RELEASE_STATUS.md`: it found **zero users and zero submissions** before the hosted migrations were applied. An empty or different database/account context is therefore the leading explanation for the current empty dashboard. This is not enough to prove which database URL the earlier screenshots used or where the earlier rows went. A user deletion is another plausible explanation because the account deletion route deletes the user, and the database foreign keys cascade to submissions and jobs; there is no deletion audit record in the inspected route. Neither cause was verified in this pass.

**Root cause remains unconfirmed. Do not restore, delete, migrate, or otherwise change hosted data based on this report.** The next diagnostic step is a read-only check of the currently authenticated GitHub account's internal user ID and per-user row counts in the exact database used by the live Render service, plus verification that the earlier dashboard used that same database and account. Do not disclose credentials or full source code as part of that check.

## Evidence inspected

- `backend/src/dashboard-routes.ts`: dashboard count and recent rows are filtered by authenticated `userId`; recent rows are sorted by `submittedAt desc`, limited to 30, with no date or status filter.
- `backend/src/sessions.ts`: session token hash resolves to a database session and its user; dashboard authentication uses that user.
- `backend/src/auth.ts`: GitHub OAuth upserts users by numeric GitHub ID. `/api/data/delete` deletes the user after best-effort provider revocation/uninstallation.
- `backend/src/extension-routes.ts`: accepted submissions are queued under `res.locals.extensionUserId`; LeetCode account mismatch is rejected before queueing.
- `backend/src/sync-queue.ts`: submission and job are created transactionally for the extension token's user ID; duplicates are keyed by user ID plus provider submission ID.
- `backend/src/sync-worker.ts`: GitHub commit precedes the `SYNCED` database update and its stored SHA.
- `backend/prisma/schema.prisma` and `backend/prisma/migrations/20261012000000_automatic_linking_and_full_submissions/migration.sql`: user/submission/job cascade relations and additive migration changes.
- `docs/RELEASE_STATUS.md`: prior record of zero users/submissions in the pre-migration Supabase preflight and later empty hosted dashboard observation.

## Not verified

- Current production database user/submission/job counts and project identity.
- Whether the live Render environment and the historical screenshots used the same database and account.
- Whether `/api/data/delete` was ever called for this account.
- Whether the hosted encryption-key rotation was run and completed.
- Whether prior GitHub commits exist for the earlier rows even if the current database no longer has them.
